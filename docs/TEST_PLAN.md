# 핵심 검증 계획

실제 협조 샵은 1곳이어도 테스트 계정은 사업자 A/B 두 개를 사용한다. 테스트는 전용 PostgreSQL/Supabase 개발 환경에서 허구 데이터로 수행한다. 새 환경에서는 아래 항목 모두 미실행 상태로 시작한다.

## R1 기반

- native Next 개발 서버가 실제 URL에서 열린다.
- 환경변수가 없어도 첫 화면이 렌더링된다.
- 환경변수 존재만으로 DB 연결 성공을 표시하지 않는다.
- typecheck, lint, production build 및 health HTTP 응답을 확인한다.
- 화면 도구를 사용할 수 없었다면 렌더링 검증 미실행으로 적는다. HTTP 200을 모바일 검증으로 대체하지 않는다.

## 인증·권한

- 익명 사용자는 사업자 예약·고객 목록·계좌 관리 테이블을 조회하지 못한다.
- A는 A의 샵만 읽고 수정한다. B의 ID를 body/path/query/RPC 인자로 넣어도 불가능하다.
- 공개 Supabase 키로 민감 RPC를 직접 호출해 Next의 검사를 우회할 수 없다.
- 서버 전용 키를 쓰는 API도 인증·테넌트 검사를 수행한다.
- 로그인 만료·로그아웃·비밀번호 재설정 흐름이 정상 동작한다.
- 서버 비밀값이 브라우저 코드·응답·로그에 나타나지 않는다.

## 원자성·시간

1. 같은 시간에 서로 다른 고객 요청 10개 → 예약·점유 한 건만 성공.
2. 서로 다른 시작 시각이라도 시술/준비 구간이 겹치면 충돌.
3. 맞닿은 종료/시작 구간은 허용.
4. 같은 키·같은 내용 동시 요청 10개 → 동일 예약 ID 및 한 번의 상태 이벤트.
5. 같은 키·다른 내용 → 충돌 오류.
6. 멱등 조회와 저장 사이에 경쟁 요청을 끼워 넣어도 중복/오판 없음.
7. 점유 삽입 중 의도적 오류 → 예약·점유·이벤트 모두 롤백.
8. 온라인/수동/차단이 서로 충돌하고 샵 A/B끼리는 충돌하지 않음.
9. 영업시간·휴식·최소 여유·예약 가능 기간·서울 날짜 경계를 일치시킴.
10. 취소 후 새 예약 → 옛 취소 재시도에도 새 점유 유지.
11. 표시 후 가격·시술시간·예약금·정책 버전 변경 → 재확인 없는 저장 금지.
12. 이전 성공 요청은 조건 변경/비활성화 뒤에도 원래 예약으로 복구.

## 예약금

- 예약금 없음 → 즉시 확정, 있음 → 실제 송금 여부와 관계없이 최초에는 입금 대기.
- 금액·계좌·기한은 당시 조건으로 고정된다.
- 고객 입금 신고는 확인 대기일 뿐 확정/입금 검증이 아니다.
- 신고/확인과 만료가 동시에 실행되면 한 가지 일관된 최종 상태.
- 만료 정리 작업이 지연되어도 새 쓰기 경로가 기한 지난 미신고 점유를 정리.
- 신고된 확인 대기는 기한 정리로 지워지지 않음.
- 만료/취소 뒤 입금 발견 → 시간 재점유 없음, 금전 후속 확인 기록.
- 금전 후속 확인 표시가 자동 환불 완료로 보이지 않음.
- A가 B의 입금 확인 상태를 변경할 수 없음.
- 고객/사업자의 반복 클릭이 이력·알림을 중복 생성하지 않음.
- 금전 후속 처리 종료와 새 신고/수납 확인이 경합해도 새 정보가 덮이지 않고 재검토 상태로 남음.
- 수동 등록도 예약금이 있는 시술은 입금 대기로 생성되며, 별도 확인 없이 확정되지 않음.

## 브라우저·기기

- 다른 브라우저/휴대폰에서 고객 무가입 예약 → 사업자 화면에 표시 → 새로고침 유지.
- 응답 유실/탭 새로고침 → 같은 키로 결과 복구, 연락처 입력 보존.
- 오래된 서비스 조건·시간 충돌 후 필요한 항목만 다시 선택.
- 작은 화면·키보드·오류 안내·색 이외의 상태 표시 확인.
- 사업자 화면 갱신이 열린 입력 폼을 지우지 않음.
- Web Push 권한 허용/거절/OS 제한/구독 저장 실패/재연결 및 실기기 수신을 구분.

## 전송·상용 운영

- 외부 전송 실패에도 예약은 유지.
- 전송 작업을 가져간 프로세스 종료 후 lease가 풀려 재처리 가능.
- 타 샵 구독 endpoint에 발송·삭제·상태 노출 불가.
- 실제 알림톡/PG는 승인된 테스트 절차와 사용자 지정 수신자·테스트 키로만 확인.
- 배포 환경 URL·로그인 리다이렉트·쿠키·DB 연결·재시작 후 데이터 유지.
- 백업을 운영과 분리된 환경에 복원해 기록 수와 제약을 확인.

## 결과 보고 양식

| --- | --- | --- | --- |
| 예: 동일 시간 10개 요청 | 개발 Postgres, 통합 테스트 | 실제 결과 입력 | 미실행이면 미실행 표기 |

테스트를 실패에서 성공으로 만들기 위해 권한·유일성·검증을 제거하지 않는다. 실패 원인과 바뀐 동작을 보고한다.
