# 예약·예약금 동작 규칙

이 문서는 제품 설계안이다. 계좌이체 확인, 환불이나 금융기관 연동이 이미 구현되었다는 뜻이 아니다.

## 1. 시간과 금액

- DB 시각은 `timestamptz`로 보관한다. API는 오프셋이 있는 ISO 8601을 사용한다. 사용자에게는 Asia/Seoul로 표시한다.
- 기존 프로토타입의 epoch 분/밀리초 혼합 타입을 그대로 복사하지 않는다.
- 점유 구간은 `[시작, 시술 종료 + 준비시간)`이다. 종료와 다음 시작이 정확히 같으면 겹치지 않는다.
- 15분 단위 점유 테이블을 사용하고 `(shop_id, slot_start)`를 유일하게 한다.
- 금액은 정수 원. 예약금 0은 ‘없음’으로 정규화한다. 고정 예약금은 시술 가격을 넘을 수 없다.
- 예약금 계좌·조건·시술명/가격/시간/준비시간/취소 정책은 예약 당시 사본을 남긴다. 수정은 새 예약에 적용한다.

## 2. 상태를 분리한다

예약 상태: `pending_deposit`, `confirmed`, `completed`, `no_show`, `cancelled`, `expired`.

입금 상태: `not_required`, `awaiting_transfer`, `reported`, `verified`.

별도 금전 후속 상태: `none`, `review_needed`, `resolved_recorded` 및 처리 이력. 마지막 값은 사업자가 앱 밖에서 확인·조치했다고 기록했다는 뜻이며 은행 이체 증명이 아니다.

| 고객/사업자 행동 | 예약 상태 | 입금 상태 | 시간 점유 |
| --- | --- | --- | --- |
| 예약금 없이 정상 신청 | confirmed | not_required | 유지 |
| 예약금 있는 정상 신청 | pending_deposit | awaiting_transfer | 기한까지 유지 |
| 고객이 기한 내 ‘입금 확인 요청’ | pending_deposit | reported | 사업자 검토까지 유지 |
| 사업자가 유효한 활성 대기의 입금 확인 | confirmed | verified | 유지 |
| 만료·취소 뒤 실제 입금 확인 기록 | expired/cancelled 그대로 | verified | 점유 없음; review_needed |
| 미신고 상태로 기한 경과 | expired | awaiting_transfer | 해제 |
| 허용된 취소 | cancelled | 기존 이력 유지 | 해제 |
| 시술 완료/노쇼 기록 | completed/no_show | 기존 이력 유지 | 과거 이력 유지 |

허용된 조합만 제약/함수로 생성한다. 만료·취소 상태에서 verified가 되는 것은 돈 확인 기록이며 예약 확정이 아니다. 입금 신고만으로 `verified`나 `confirmed`가 될 수 없다. 예약금 있는 예약을 일반 상태 PATCH로 확정하지 못하게 한다.

## 3. 예약금 사용 여부와 흐름

사업자는 시술별로 ‘예약금 없음’ 또는 ‘고정 금액’을 선택한다. 은행·계좌번호·예금주는 샵 공통 설정으로 두고, 유효한 계좌와 고객에게 보여줄 예약금/취소 안내가 있어야 예약금 있는 시술을 공개할 수 있다.

R4에서는 공개 중인 예약금 시술이 있으면 계좌 삭제나 예약금·취소 안내 제거를 거절한다. 시술 공개와 계좌·정책 수정은 같은 샵 행 잠금을 사용한다. R5는 고객 예약 당시 조건을 저장하고, 고객의 이체 신고와 만료를 처리한다. R7은 은행 내역을 직접 확인한 사업자가 입금과 금전 후속 처리를 기록할 수 있게 한다.

고객은 예약 제출 전에 시술 총액, 예약금, 나머지 금액, 입금 신고 기한, 사업자 확인 후 확정됨을 본다. 제출 후 본인 예약 확인 페이지에서 해당 예약의 계좌 사본과 절대 기한을 확인한다.

사업자 수동 등록에도 시술의 예약금 규칙을 적용한다. 예약금이 있으면 입금 대기로 생성하고 별도의 입금 확인 동작으로 확정한다. 수동 등록이라는 이유로 입금을 확인한 것으로 처리하거나 예약금을 면제하지 않는다. 수동 등록은 공개 최소 예약 여유를 예외로 할 수 있으나 과거 시각·영업 조건·중복 점유 검증은 유지한다.

계좌이체는 고객과 해당 샵 사이에서 이루어진다. 이 SaaS가 금액을 받아 보관하거나 나눠 보내지 않는다. 고객의 신고 버튼은 확인 요청일 뿐이다.

## 4. 기한과 사업자 확인

- 초기 입금 신고 기한은 생성 후 60분이다. 샵이 30/60/120분으로 바꿀 수 있으며 예약 시작 시각보다 늦어질 수 없다.
- 서버 DB 시각으로 판단한다. 정확히 기한에 도달하면 미신고 예약은 만료 대상이다.
- 기한 안에 신고된 예약은 자동 만료 대상에서 제외한다. 실제 입금을 했는데 사업자가 시술 중 확인하지 못한 경우를 보호하기 위한 운영 제안이다.
- 확인 대기 상태가 최초 기한을 넘으면 관리 화면에 ‘입금 확인이 지연되고 있어요’를 표시하고 시간은 유지한다. 무조건 자동 확정하거나 자동 해제하지 않는다.
- 입금 확인은 해당 샵 사업자만 할 수 있다. ‘은행 입금내역을 확인했습니다’ 확인 동작을 거쳐 확인자·시각·이벤트를 기록한다.
- 미신고라도 사업자가 기한 내 직접 입금을 확인하면 확정할 수 있다. 기한이 지난 미신고 pending_deposit은 정기 정리가 아직 실행되지 않았어도 먼저 expired로 처리한다.
- 확인 팝업에는 요구한 예약금을 표시한다. 부분·과입금은 실제 금액과 사유를 별도 이벤트로 남긴다. 예약은 입금 대기에 두고, 미신고로 만료되면 금전 후속 확인 목록에 둔다.
- 사업자가 입금이 없음을 확인한 경우 예약을 취소할 수 있다. 고객이 신고한 건을 자동으로 미신고로 되돌려 만료시키지 않는다.
- 만료 뒤 입금 신고는 시간을 되살리지 않는다. 고객에게 샵 문의 안내와 후속 확인 요청을 제공하고, 금전 후속 상태를 `review_needed`로 기록한다.
- 이미 만료·취소한 건에 실제 입금이 발견되면 기존 예약을 부활시키지 않는다. 환불 또는 새 예약을 사업자가 결정하고, 새 예약은 다시 가능 시간 검증을 거친다.

이 방식에서는 입금 확인 대기 건이 오래 시간을 막을 수 있다. 첫 샵 검증에서 확인 부담과 허위 신고를 관찰한다. 반복 허위 신청 방어는 요청 제한·이력으로 시작하며, 필요가 확인되면 추가 인증을 설계한다.

## 5. 취소와 환불

- 입금 대기 예약은 예약 시작 전 고객이 취소할 수 있다. 이미 확정된 고객 예약은 해당 예약에 저장된 취소 마감 조건을 따른다.
- 사업자는 본인 샵의 활성 예약을 취소할 수 있다. 사유를 기록하고 상태 변경 이력을 남긴다.
- 취소 시 시간은 해제하지만, 신고/확인된 입금 이력은 지우지 않는다. 금전 후속 상태를 `review_needed`로 둔다.
- 환불 필요 여부와 액수는 샵 정책과 실제 상황을 사업자가 확인한다. R7에서는 은행에서 이미 처리한 환불 금액이나 환불 없이 정리한 사유를 기록할 수 있다.
- 앱에서 ‘처리 기록 남기기’는 금액·시각·메모를 보관하는 행위다. 은행 송금 성공으로 표시하지 않는다.
- `resolved_recorded` 이후 새로운 입금 신고/확인 정보가 접수되면 `review_needed`로 다시 열고 이전 처리 이력을 보존한다. 처리 기록을 닫을 때는 화면에 표시한 최신 금전 이벤트 버전을 검사한다. 새 이벤트가 추가됐다면 재확인을 요청하며 오래된 화면이 새 요청을 덮지 못하게 한다. 종료 예약의 첫 늦은 신고와 최초 실제 수납 확인은 후속 확인을 다시 열 수 있다. 수동 환불 기록의 누계는 기록된 수납액을 넘을 수 없다.
- 완료/노쇼는 예약 시작 이후 확정 예약에서만 처리한다. 완료/노쇼 이력을 고치는 동작은 별도 감사 이력을 남기며 시간을 다시 열지 않는다.

R6에서 사업자는 시작 전의 확정·예약금 대기 예약을 옮길 수 있다. 시술·가격·예약금·계좌·정책 사본과 기존 입금 기한을 보존한다. 기존 입금 기한보다 앞선 시작 시각은 거절한다. 수동 등록과 사업자 시간 변경은 공개 최소 예약 여유를 적용하지 않으며, 현재 영업시간·휴식·예약 가능 기간과 15분 점유 규칙을 따른다. 예약금이 설정된 취소는 기존 입금 상태를 보존하고 금전 후속 확인 필요로 기록한다.

## 6. 만료 정리와 동시성

브라우저 타이머는 표시용이다. 탭을 닫거나 Render 서버가 재시작해도 기한 판단은 DB에 남아야 한다.

- 모든 점유 변경은 샵 행 잠금 → 예약 행 잠금 순서로 수행한다.
- DB 트랜잭션 안에서 잠금을 얻은 뒤 기준 시각을 다시 얻어 기한을 판정한다. 오래 기다린 요청의 시작 시각으로 승인하지 않는다.
- 신규 예약/수동 등록/시간 차단 전에 그 샵의 미신고 만료 건을 정리하고 점유를 해제한다.
- 같은 트랜잭션에서 가능 시간과 버전을 확인하고 예약·점유·이벤트를 저장한다.
- 정기 작업은 별도로 만료 상태를 정리한다. 정기 작업이 늦어져도 새 예약 쓰기 경로가 만료 건을 정리하므로 시간을 영구 차단하지 않는다.
- 조회에서 만료될 미신고 예약을 빈 시간으로 판단할 수 있지만, 최종 예약은 반드시 같은 규칙의 DB 쓰기 경로로 검증한다.
- 입금 신고/사업자 확인/취소/만료도 같은 잠금과 상태 조건을 쓴다. 기한과 경합하면 트랜잭션의 권위 있는 시각·상태에 따라 한 결과로 확정한다.
- 만료/취소 재시도는 그 예약의 점유만 해제한다. 새 예약이 같은 시간을 차지했으면 손대지 않는다.
- cron은 샵 단위로 짧게 처리한다. 여러 샵을 한 트랜잭션에 묶는 경우 잠금 순서를 통일한다.

## 7. 재전송과 결과 복구

예약 제출 전 32바이트 난수 고객 토큰, 재시도 키, 원래 입력 및 확인한 조건을 탭의 sessionStorage에 저장한다. 저장할 수 없으면 제출 전 복구 불가 상태를 안내한다. 개인정보가 있는 진행 기록은 최소한으로 보관하고 예약 생성 결과(입금 대기도 포함)를 확인하고 관리 링크를 확보한 뒤, 또는 명백한 거절 뒤 제거한다.

서버는 토큰 해시와 재시도 키 및 정규화 요청 해시를 저장한다. 같은 키/같은 내용은 동일 예약을 반환하고, 다른 내용이면 충돌로 거절한다. 입금 신고·확인·취소 이벤트도 중복 생성하지 않는다.

실패 응답이 없었다는 이유로 성공을 표시하거나, 한 번의 404를 보고 새 키로 다시 제출하지 않는다. 성공 이력을 먼저 확인하고 원래 요청으로 재시도한다. 만료된 옛 요청의 재전송은 만료된 동일 예약을 보여주며 새 예약을 만들지 않는다.

R5는 탭에 처리 중 요청을 보관한다. 응답이 불확실하거나 예약이 없다는 응답이 오면 원래 키·입력·토큰으로 재조회한다. 생성 RPC는 동일 토큰의 재전송을 먼저 직렬화하므로 샵 주소가 바뀌어도 이미 저장된 요청을 복구한다.

## 8. 공개 접근 최소화

공개 샵 페이지에는 상호·서비스·정책·가능 시간만 제공한다. 샵 전체 고객 정보·예약 목록·은행 상세를 공개 목록 API에 담지 않는다. 은행 안내는 해당 예약의 확인 토큰으로 접근하는 페이지에서 필요한 범위로 제공한다.

전화번호나 예약번호만으로 예약을 조회하지 않는다. 확인 토큰은 URL query/path 대신 fragment에서 읽어 Authorization 헤더로 전달한다. 확인 페이지에는 전화번호 일부만 표시하고 서드파티 추적 스크립트로 토큰이나 개인정보가 흘러가지 않게 한다.

## 9. 사업자 알림

예약 생성·입금 신고·만료 이벤트는 같은 트랜잭션에서 앱 알림과 발송 작업을 기록한다. 기한이 지나도 신고된 예약은 점유를 유지하며 사업자에게 입금 확인 지연을 안내한다. 당일 예약은 서울 날짜 기준으로 안내한다. 푸시 전송 실패는 예약 상태, 점유, 입금 기록에 영향을 주지 않는다. [알림 기준과 운영 설정](R8_NOTIFICATIONS.md)
