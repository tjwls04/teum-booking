# 기술 구조와 마이그레이션 기준

## 1. 선택한 구성

| 용도 | 선택 | 이유 |
| --- | --- | --- |
| 화면·서버 API | native Next.js App Router, TypeScript, React | 학습한 도구로 하나의 저장소에서 관리 |
| 데이터베이스·로그인 | Supabase PostgreSQL, Auth | 별도 소유 DB, 관계형 제약·트랜잭션·권한 |
| 버전 관리 | 사용자 GitHub 비공개 저장소 | 코드·SQL·결정 이력 보관 |
| 호스팅 | Render Node Web Service | Next 서버 실행, GitHub 배포 |
| 오류 추적 | Sentry, 실사용 전 추가 | 개인정보 제외 후 운영 오류 확인 |
| API 확인 | Postman + 자동 통합 테스트 | 수동 재현과 핵심 회귀 검증 |

Node는 Next의 실행 환경이다. Express 서버를 따로 만들지 않는다. DB 기반 만료·작업 기록을 이용하므로 초기 Redis는 불필요하다. 별도 전역 상태 문제가 생기기 전 Zustand를 도입하지 않는다. Google Cloud·추가 ORM·메시지 큐 제품은 현재 필수 요소가 아니다.

## 2. 소유와 데이터 격리

사용자 계정에 하나의 Supabase 프로젝트를 만들고, 서비스와 독립적으로 DB를 관리한다. 각 샵마다 별도 DB를 만들 필요는 없다. 동일 DB 안에서 `shop_id`와 RLS로 샵 데이터를 격리한다.

개발·운영 환경은 분리한다. 운영 DB에 테스트 데이터나 파괴적 테스트를 넣지 않는다. 환경별 비용·활성 프로젝트 수는 생성 시 확인한다.

## 3. 주요 테이블

| 테이블 | 핵심 역할/제약 |
| --- | --- |
| shops | owner_user_id는 auth.users의 UUID, owner 유일, 공개 slug 유일, 영업·정책 revision |
| shop_weekly_periods | 샵·ISO 요일별 영업 및 휴식 구간, 서울 자정부터 경과한 분 |
| services | shop_id, 시간/금액/예약금 조건, 활성 여부, revision |
| shop_bank_accounts | 샵 계좌 설정, 공개 전체조회 금지, 소유자 제한 |
| bookings | 샵/시술/고객 정보, 상태, 당시 조건 사본, 확인 토큰 해시, 재시도 키/요청 해시 |
| occupied_slots | shop_id + slot_start PK, booking_id 또는 block_id 중 하나, 다른 샵 FK 연결 금지 |
| blocks | 샵별 차단 구간과 사유 |
| booking_events | 예약 변경 이력, 중복 방지 키, 확인자/시각 |
| r8_private.inbox · jobs · deliveries | 알림·읽음 상태, 원자적 작업 생성, 기기별 lease·전송 결과 |
| r8_private.devices · settings | 샵별 푸시 설정과 구독, 허용 endpoint 범위 |
| rate_limits | 공개 쓰기 제한을 위한 원자적 카운터, 만료/정리 |

테이블 이름은 구현에서 정리할 수 있으나 핵심 제약은 유지한다. UUID를 새 프로젝트 기본 ID로 사용하고 시간은 timestamptz, 금액은 정수 원으로 통일한다. 이전 문자열 ID와 시간을 그대로 섞지 않는다. 기존 실제 데이터가 발견되면 매핑·백업·이행 계획을 별도로 작성한다.

R9는 시술 생성의 멱등 키를 DB 진입점에서 강제하고, 샵에 저장할 예약 창을 오늘 포함 90일로 제한한다. 공개 API는 개별 IP 제한을 먼저 적용하고, 확인된 샵 UUID로 조회·생성·확인·입금 신고의 한도를 각각 계산한다. [R9 배포 순서와 점검](R9_DEPLOYMENT.md)

R2에서는 샵부터 예약 이벤트까지의 테이블과 RLS를 추가했다. 알림 작업·푸시 구독·요청 제한은 각 기능 단계에서 추가한다. [R2 실행 순서와 권한 범위](R2_DATABASE.md)

## 4. 인증·API 경계

- 사업자: Supabase Auth + 공식 Next.js 서버 인증 패턴. 서버에서 검증한 사용자 ID로 샵을 찾는다.
- 사업자 읽기: 사용자 세션과 RLS를 적용한다. 다른 사업자 ID를 body/query로 보내도 접근되지 않는다.
- 중요한 쓰기: Next Route Handler → 서버 전용 RPC. 로그인 사용자 ID는 서버가 검증해 전달하고 DB 함수가 소유권을 재검사한다.
- 고객: 공개 Next API → 제한된 서버 RPC. 공개 Supabase 키로 예약 테이블이나 생성 RPC를 직접 열지 않는다. rate limit을 우회할 수 없도록 RPC 실행 권한도 닫는다.
- 서버 전용 키는 서버 모듈에서만 사용한다. 서버 역할은 RLS를 우회할 수 있으므로 명시적 테넌트 검사와 반환 컬럼 제한이 필수다.
- 기본 실행 권한을 제거하고 허용한 역할만 RPC를 호출하도록 한다. 필요한 경우 SECURITY DEFINER에 고정 search_path와 명시적 스키마·소유권 검사를 둔다.
- 서버 검증, 요청 크기 제한, 출처 검사, rate limit, 구조화된 오류를 적용한다. 클라이언트 검사만으로 처리하지 않는다.

R2의 브라우저·서버 클라이언트에는 공개 publishable key를 사용한다. 사업자 읽기는 소유 샵에 한하며 예약 확인 토큰 해시, 요청 해시, 예약 당시 계좌 사본은 사업자 세션의 직접 조회에서 제외한다. R2 테이블에 대한 앱 역할의 직접 쓰기는 닫아 둔다. R4 설정 쓰기는 이메일 인증 사업자의 JWT를 받는 소유자 한정 RPC를 사용한다. R3에서는 대시보드 Proxy가 세션을 갱신하고 페이지가 Supabase Auth에서 사용자 정보를 검증한다. 이메일 링크의 임시 세션은 서버 요청 안에서만 사용한다. [R3 인증 안내](R3_AUTH.md)

R4는 기존 테이블을 유지한다. 네 설정 RPC는 SECURITY DEFINER의 검색 경로를 비우고, 이메일 인증과 샵 소유권을 확인한다. 명시적으로 허용한 authenticated 역할만 실행할 수 있으며 보조 함수는 비공개 스키마에 둔다. 샵 정보·시간·정책·계좌 변경은 샵 행을 잠근 뒤 정책 버전을 검사하고 증가시킨다. 시술 변경도 같은 샵 행을 먼저 잠그고 시술 버전을 검사한다. 샵 최초 등록 재시도는 이미 생성한 샵을 반환한다.

## 5. 원자적 예약

한 RPC/트랜잭션에서 기존 멱등 처리 조회 → 샵 잠금 → 재조회 → 만료 정리 → 서비스/샵 revision·시간 검증 → 예약·점유·이벤트 저장을 처리한다.

같은 시간의 서로 다른 고객 요청은 하나만 성공한다. 동일 요청의 재전송은 동일 결과다. 여러 `supabase.from(...).insert(...)`를 호출한 뒤 마지막에 실패를 표시하는 방식은 원자성을 보장하지 못한다.

잠금만으로 끝내지 않고 점유 유일성 제약을 함께 사용한다. 서비스·정책 변경과 수동 예약·차단도 같은 샵 잠금을 따른다. 구간 기준은 BOOKING_RULES에 정의되어 있다.

R2 점유표의 기본키는 `(shop_id, slot_start)`다. 복합 외래 키로 예약·차단과 점유의 샵이 같아야 한다. 각 활성 예약·차단의 전체 슬롯 생성 및 해제, 멱등 재시도와 이벤트 기록은 후속 쓰기 RPC가 동일 트랜잭션에서 처리한다.

R5에서 공개 예약 API는 요청 본문을 최대 4KiB로 제한하고 동일 출처에서만 받는다. 서비스 키가 필요한 RPC는 샵 공개 주소 또는 확인 토큰 해시로 범위를 한정하고, 항상 저장된 조건으로 최종 검증한다. 조회는 하루만 받으며 서울 기준 오늘부터 최대 90일(오늘 포함)의 시작 날짜를 제공한다. 요청 빈도는 PostgreSQL의 고정 크기 버킷에서 전체·샵별로 제한하고, 신뢰한 인입 프록시가 제공하는 단일 IP를 설정한 경우 IP 제한도 적용한다.

예약 생성은 토큰 기준 자문 잠금 후 샵 행을 잠근다. 그 뒤 기존 성공 이력, 설정 버전과 가용 시간을 확인하고 예약·슬롯·이벤트를 하나의 트랜잭션으로 기록한다. 만료는 예약 생성, 토큰 확인 또는 사업자 목록·상세 조회 시 처리하며, 가용 시간 조회에서는 기한이 지난 미신고 점유를 제외한다. [R5 실행 및 검증 기록](WORKLOG.md#2026-11-27--r5-고객-예약)

R6 사업자 관리 RPC는 로그인 세션의 소유 샵을 확인한다. 예약 변경은 샵 행 다음에 예약 행을 잠그고 예약 버전을 검사한다. R5의 이체 신고와 만료가 예약을 갱신할 때도 동일한 버전이 올라간다. 시간 변경·취소와 점유·이벤트는 트랜잭션 경계 안에 있으며 시술·정책 사본은 보존된다. 해제한 차단은 해제 시각을 남긴다. 캘린더 조회는 서울 기준 최대 42일이며 일정별 표시 한도는 예약과 차단 각 500건이다.

## 6. 만료와 알림

입금 기한 정리는 PostgreSQL 함수와 Supabase Cron을 기본안으로 둔다. 쓰기 경로에도 만료 정리를 넣어 cron 지연이 정확성을 좌우하지 않게 한다. 운영에서는 정리 작업 실패·밀림을 확인한다.

R7 금전 RPC는 샵 행과 예약 행을 순서대로 잠그고 예약 버전을 확인한다. 입금 확인 전에 미신고 만료를 정리한다. 종료 예약의 수납, 부분·과입금, 수동 환불 또는 환불 없음은 예약 이벤트에 금액·사유·확인자를 기록한다. 같은 요청 키와 내용의 재시도는 기존 이벤트를 반환한다.

### R7 정기 만료 설정

개발 DB에 R7을 적용한 뒤 Supabase Dashboard의 Integrations에서 Cron을 활성화한다. SQL Editor에서 마이그레이션 소유자인 `postgres`로 다음 작업을 등록한다. 앱 사용자, 공개 키, 서버 API 키에는 만료 함수 실행 권한이 없다. [Supabase Cron 설정](https://supabase.com/docs/guides/cron/quickstart)

```sql
select cron.schedule(
  'teum-r7-expire-deposits',
  '* * * * *',
  'select r7_private.expire_due();'
);
```

한 번에 잠긴 샵을 건너뛰며 최대 25개 샵, 샵당 100건을 정리한다. Cron 실행 이력에서 성공을 확인하고 기한 지난 미신고 건의 상태와 점유 해제를 확인한다. 정기 실행이 늦어져도 기존 조회·쓰기 경로에서 만료를 처리한다.

R8은 예약 이벤트 트리거로 알림과 작업을 이벤트와 같은 트랜잭션에 저장한다. 제한된 서버 RPC가 만료형 lease로 발송을 임대하고 제공사 응답을 별도로 기록한다. 앱 사용자 역할은 소유권을 재확인하는 알림·기기 RPC만 호출한다. 내부 워커를 예약·입금 상태 변경 경로에서 호출하지 않는다. [R8 운영 및 실기기 확인 방법](R8_NOTIFICATIONS.md)

## 7. 이전 프로토타입에서 참고할 것

| 재사용 후보 | 새 환경에서 바꿀 것 |
| --- | --- |
| 한국어 문구와 고객 흐름 | native Next 빌드/실행, 시각 기준은 [DESIGN.md](DESIGN.md) |
| 순수 시간·입력 규칙의 아이디어 | Cloudflare Worker env/waitUntil 대신 Node와 영속 작업 처리 |
| 충돌·멱등·취소·격리 테스트 시나리오 | D1/SQLite SQL 대신 PostgreSQL 마이그레이션·RPC·RLS |
| 입력 보존·요청 복구 UX | ChatGPT 헤더 로그인 대신 Supabase Auth |
| 예약 조건 사본·revision 개념 | 기존 epoch 분/밀리초 대신 일관된 timestamptz |

이전 27개 D1 테스트의 통과 기록은 참고일 뿐, 새 환경의 테스트 결과에 더하지 않는다.

## 8. 배포·비용 기준

개발은 로컬 + 무료 개발 DB로 시작한다. 상용 기본 예산안은 Render 소형 유료 Node 인스턴스 약 US$7/월 + Supabase Pro 첫 프로젝트 기본 US$25/월 = 약 US$32/월이다. 도메인·이메일·메시지·세금·추가 사용량이 포함된 고정 견적은 아니다. 메모리/응답시간을 측정해 필요할 때 크기를 조정한다.

Supabase 기본 SMTP는 실제 외부 사업자의 가입·비밀번호 재설정용으로 가정하지 않는다. 상용 전 별도 SMTP를 설정하고 실제 메일 흐름을 확인한다. 유료 DB 플랜만 선택한다고 메일 설정이 완료되는 것은 아니다.

인프라 구매·외부 계정 생성은 아직 실행하지 않았다. 코드, DB, 호스팅 연결을 각 단계에서 사용자 계정으로 진행한다.
