# 단계별 구현 계획

달력상의 완료 날짜는 계정·계약·실기기 검증 상태에 따라 달라진다. 단계의 완료 기준으로 진행하며, 첫 작업은 R1만 실행한다.

| 단계 | 구현 단위 | 완료 증거 |
| --- | --- | --- |
| R1 | native Next 기반 및 미연결 상태 안내 | 로컬 실행, typecheck/lint/build, health 응답 |
| R2 | Supabase 개발 환경·샵/시술 스키마·RLS | Git SQL, 비파괴 적용, A/B/익명 권한 테스트 |
| R3 | 사업자 이메일 인증·세션·대시보드 보호 | 테스트 계정의 가입·인증·로그인·로그아웃·재설정 및 세션 확인 |
| R4 | 샵 온보딩·시술·영업시간·예약 정책·계좌 설정 | 소유자 한정 RPC, 시간 중복 검증, 설정 저장 및 읽기 |
| R5a | 공개 고객 예약, 초기 예약금 상태·이체 신고 및 요청 복구 | Postgres 동시성·멱등·롤백, 모바일 예약 흐름 |
| R6 | 사업자 캘린더, 수동 예약·시간 변경·취소·완료·노쇼, 시간 차단·해제 | 같은 점유 기준, 변경 롤백, 취소 후 재예약, 샵 격리 |
| R7 | 사업자 입금 확인·금전 후속·수동 환불 기록과 정기 만료 | 승인·만료·취소 경합, 종료 일정 보존과 중복 기록 방지 |
| R8 | 사업자 알림과 PWA Web Push | 트랜잭션·중복 방지·lease 복구·격리 및 실기기 확인 |
| R9 | Render 개발 배포·Supabase 환경 분리 | 직접 URL, 다른 기기 로그인·공개 무가입 예약 |
| R10 | 사업자 1곳 비공개 검증 | 업무 개입 횟수/문제 재현/수정 결과 기록 |
| R11 | 유료 출시 조건 | SaaS 수납·해지·권한·운영 정책·백업 복원 확인 |
| R12 | 승인된 카카오 알림톡 | 실제 발신 설정·템플릿·테스트 수신, 실패 재처리 |

R2 실행 순서와 검증 결과는 [R2 데이터베이스 안내](R2_DATABASE.md) 및 [작업 기록](WORKLOG.md)에 정리한다.

이메일 템플릿과 사용자 검증 절차는 [R3 인증 안내](R3_AUTH.md)를 따른다. R5의 고객용 가능 시간은 [공개 예약 API 구조](ARCHITECTURE.md#5-원자적-예약)를 참고한다. R8 기기 지원과 Cron 설정은 [사업자 알림 운영 안내](R8_NOTIFICATIONS.md)를 따른다. R9 통합 검증과 HTTPS 데모 설정은 [발표·제한 테스트 배포 안내](R9_DEPLOYMENT.md)에 정리한다.

R12는 채널 준비가 빠르면 알림·배포 준비와 병행할 수 있다. 카카오 대기 때문에 예약 데이터와 권한 구현을 미루지 않는다. 반대로 실제 발송을 확인하기 전 카카오 알림을 판매 기능으로 약속하지 않는다.

## 작업 요청문의 형태

각 단계마다 읽을 파일, 이번 변경, 유지할 동작, 포함하지 않을 기능, 완료 기준, 보고 항목을 전달한다. 앞 단계에서 실제 발견한 구조와 오류를 반영해서 다음 요청문을 조정한다.

첫 단계 결과를 보지 않고 R2 이후를 한꺼번에 생성시키지 않는다. 다음 작업은 현재 파일·Git diff·검증 결과를 기준으로 좁혀 맡긴다.

## 첫 샵 확인 준비

테스트 사업자에게는 현재 시술 목록/시간/준비시간, 영업시간·휴식, 예약금/입금 확인 방식, 취소 사례를 확인한다. 실제 고객 이름·전화번호·은행 거래내역을 이 대화에 가져올 필요는 없다. 업무 형태를 익명으로 정리하면 된다.

## 유료 출시 전 해결할 실제 설정

- 서비스 운영자 정보와 이용료 수납·해지·환불 안내, 실제 제공 기능과 가격.
- 사업자 계정 이메일 전송, 비밀번호 재설정, 세션 종료.
- 계정별/샵별 데이터 접근, 보관·삭제 절차, 오류 추적의 민감정보 제외.
- DB 백업과 별도 테스트 환경 복원, 장애 시 수동 운영 방법.
- 고객 예약 확인 링크·사업자 휴대폰 알림의 실기기 결과.
- SaaS 결제 성공·실패·중복·구독 종료에 따른 권한. PG 계약 전에는 테스트 환경으로 검증.

일반 예약과 예약금 직접 이체를 먼저 검증하고, 플랫폼이 돈을 수납·분배하는 기능은 별도 요구·계약 단계로 다룬다.
